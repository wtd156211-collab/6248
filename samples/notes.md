# 现场记录

时间：2026-09-24，来源：路口保障反馈，用到的样本都在 `samples/` 下。

## 现象

导航在 `n4_detour` 的 A 路口给出了一条违章路线。

- 查询：`samples/queries/n4_detour.json` 的 `q1`（S → B）。
- 现在的做法：先在节点图上算最短路，拿到结果之后才去比对禁转表；命中了也不重算，直接返回。
- 返回的路线：`S-A` → `A-B`，代价 4。
- 实际情况：沿 `S-A` 驶入 A 之后左转上 `A-B` 是禁止的，路口有抓拍，司机照导航走被拍了。
- 人工走的合法路线：继续向东 `A-C`，再经 `C-D`、`D-B` 绕回 B，代价 8。

同一张表上还有另一种情况：`q3`（S → D）忽略限制时给出 `S-A` → `A-B` → `B-D`，代价 6，也踩了同一条禁转；合法解同样是 6，走的是 `S-A` → `A-C` → `C-D`。总代价一样、路线完全不同，只看代价对不出来。

`n2_parallel` 是同一类问题的另一个例子：便宜的那条平行边 `A-B#1` 之后两个出口都被禁，忽略限制算出来 6，实际只能走 `A-B#2`，代价 8。

## 现在的实现方式

- 禁转表只在算完之后校验一次，没有进入搜索；
- 搜索状态只记节点，不记「从哪条边进来」，所以两处禁转都漏判了；
- 平行边与单向路都按普通边处理，边 id 有区分，但搜索里只用节点；
- 页面上画的是忽略限制算出来的路线，看起来比实际能走的更短。
